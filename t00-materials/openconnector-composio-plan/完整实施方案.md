# OpenConnector Composio 兼容网关
## Multica 接入、生产化、安全验收与上游升级完整实施方案

**版本：** 1.0  
**编制日期：** 2026-10-02  
**状态：** 待实现的工程规格；不是已完成开发、测试或部署的报告。  
**首个兼容目标：** `multica-core-v1`，以文中固定的 Multica 提交为契约基线。  
**推荐形态：** 独立 Go 网关 + Multica 有限补丁 + OpenConnector 两类通用补丁。

> 核心决策：让 OpenConnector 承担凭据保管与第三方 Action 执行，让兼容网关承担 Composio API 外观、多用户归属、受限会话和契约转换。首版保证 Multica 的连接与任务执行链路，不承诺完整复刻 Composio。

本文中“必须”是验收约束，“建议”是可调整设计；所有标注“拟新增”的接口、字段、配置和能力都需要实现，不能当作上游已有功能。

## 1. 结论与不可妥协的边界

采用独立兼容层是可行的，但生产方案不能缩减为 BaseURL 转发。

必须同时满足：

1. Multica 现有应用目录、连接账号、回调校验和应用授权链路继续工作。
2. Agent 只取得会话执行凭据，不能取得控制面项目 Key、OpenConnector 管理员 Token 或第三方 OAuth 凭据。
3. 项目、用户、Agent、连接与具体 Action 的权限分别校验；连接别名不充当用户身份。
4. 同一 provider 的多人 OAuth 不能相互取消；旧回调不能覆盖新连接。
5. “本地禁用”“第三方撤权成功”“删除凭据”是三个独立事实，不用一个成功响应混淆。
6. 网络超时、取消或未知执行结果不触发写操作自动重放。
7. 兼容声明必须绑定版本、接口及测试证据；未实现能力明确拒绝，禁止假成功。

前期可以做仅供开发验证的受限原型；上线门槛必须包含安全补丁和失败路径，而不只包含正常调用。

### 2.2 与方案直接相关的现状

- Multica 的 Composio SDK 支持 `Options.BaseURL`，但本次核对的启动接线只传入 APIKey。[M1][M2]
- Multica 业务层通过有限 SDK 接口完成目录、授权配置、账号和会话操作；回调还会校验连接归属。[M3][M4]
- 任务派发使用 Agent 所有者的连接，按应用白名单与有效连接求交集，生成 MCP 配置。[M5]
- 当前 MCP 鉴权头由 `MCPAuthHeaders()` 返回项目级 `x-api-key`。[M1][M5][M6]
- OpenConnector 的管理身份在连接路由中固定为 `local-admin`；其请求存储按 owner 与 service 替换尚未处理的旧授权请求。[O1][O2]
- OpenConnector 持久化 Token 的 `allowedConnections` 省略或为空数组表示不限制连接；非空数组才是精确连接 ID 授权。[O3]
- 当前删除连接接口可选择尽力撤权，但会先删除凭据；返回的撤权结果可能为 `done`、`failed`、`unsupported` 或 `skipped`。[O3]
- Action HTTP 接口支持 `Idempotency-Key`；原生 MCP 的 `execute_action` 不接受该幂等键。[O3]

## 3. 兼容范围与产品声明

### 3.1 分层兼容

| 兼容层级 | 首版承诺 | 明确不等价于 |
|---|---|---|
| HTTP 核心契约 | Multica 使用的目录、auth config、连接与 session 请求/响应 | 全部 Composio REST API |
| MCP 传输 | 初始化、工具发现、调用、协议错误和受限 HTTP 会话 | 完整 MCP OAuth 发现与注册服务 |
| Agent 工具能力 | 使用受限目录发现并执行经准入的 OpenConnector Actions | Composio 全部元工具及工具 slug 语义 |
| 连接生命周期 | 真实授权、用户归属、禁用、撤权结果、删除 | 承诺所有 provider 都能远程撤销授权 |
| 客户端兼容 | 固定 Multica 提交与验收过的运行时组合 | 任意 Composio Python/TypeScript SDK 版本 |

建议对外表述为：

> “兼容 Multica Composio 接入子集；底层使用 OpenConnector；支持范围以兼容矩阵为准。”

### 3.2 首版范围

首版完成单个部署项目、多用户、每用户每 toolkit 一个当前有效账号、限定 provider 与 Action 白名单、完整连接与撤销体验、会话级授权和运行审计。

第一轮真实联调只开放只读 Action。写操作、通用 API proxy、文件转运、provider triggers、Workbench、远程 Bash、全量工具 slug 映射、多账户任意切换、Marketplace/SaaS 混合执行均不作为首版默认能力。

连接类型按 provider 分别准入。API Key 可用于技术验证，但不能因此宣称其远程撤权已兼容。生产开启某个 provider 前，必须明确其 OAuth、权限、撤权与错误语义。

### 3.3 两条工具路线

**首版 `native-tools-v1`：** 网关向 Agent 提供发现与执行工具，语义以经过快照核验的 OpenConnector 工具为基础；不强制模仿 `COMPOSIO_*` 工具名。派发代码消费 MCP URL 而非固定工具名，但必须回归实际提示词、Skill 和运行时。[M5][O3]

**后续 `composio-meta-subset-v1`：** 按真实调用方需求适配 Composio 元工具、工具 slug、参数及返回值。Composio 的会话 API 还包含搜索、执行、连接、代理、挂载文件等能力；不能由一个 session 创建接口推导出这些能力都已兼容。[C1][C2]

如已有提示词硬编码 Composio 工具名，优先修正为中性发现流程；确需保留时，单独实施并测试对应元工具，不静默替换返回契约。

## 4. 总体架构与技术选择

### 4.1 服务边界

```text
Multica Server ──控制凭据/mTLS──> 兼容控制面 /api/v3.1/*
                                  │
                                  ├─ 项目与用户归属
                                  ├─ 连接、授权事务、会话与策略
                                  └─ PostgreSQL / 可靠任务与审计

用户浏览器 ──HTTPS──> 兼容连接页 /connect/*
                          │
                          └─ OpenConnector OAuth callback
                              └─ Multica 登录身份确认 → 完成绑定

Multica Agent ──会话 Bearer──> 兼容 MCP /sessions/{id}/mcp
                                  │
                                  └─ 精确连接与 Action 授权
                                      └─ OpenConnector HTTP Action API
                                           └─ 第三方服务

OpenConnector 管理面：仅兼容服务的管理组件可访问
OpenConnector 运行时：仅兼容服务的执行组件可访问
第三方凭据：留在 OpenConnector，不进入 Agent
```

兼容 MCP 是协议与授权终止点，不是把 Agent 的 JSON-RPC 请求无条件反向代理到全局 `/mcp`。

### 4.2 推荐技术

网关采用 Go、HTTP 服务和 PostgreSQL；MCP 采用官方 Go SDK，具体依赖版本由协议测试确定并锁定。[P1] 原因是可直接使用真实 Multica Go SDK 做客户端契约验证，同时不需要把 OpenConnector 的 TypeScript 实现嵌入 Multica。

OpenConnector 保持独立 Node 运行时。跨服务只使用 HTTP 和明确的扩展接口，不读取对方数据库、不导出 OAuth Token，不复制 provider executor。

网关、Multica、OpenConnector 使用不同数据库角色和独立迁移。初版可靠队列可基于网关 PostgreSQL 与 outbox 实现，不必须增加 Redis；未来扩容再按测量结果选择。

### 4.3 网络暴露

控制面与数据面使用不同监听器、主机或网关策略。公网只暴露必需的浏览器连接页、OAuth callback 和 MCP 入口。关闭 Agent 到控制面及 OpenConnector 原生管理面的网络通路。

即使有网络隔离，数据面也必须拒绝项目管理 Key。项目 Key 和会话 Bearer 不可互换；日志中不记录任何 Key 或 Bearer 值。

## 5. HTTP 兼容契约

根路径使用 `/api/v3.1`。以下属于本项目目标，不代表 OpenConnector 已提供这些兼容路由。

| 兼容接口 | 必要行为 | 底层实现/约束 |
|---|---|---|
| `GET /toolkits` | 分页、目录、名称、slug、可用元数据 | 目录与本项目准入配置求交集 |
| `GET /toolkits/{slug}` | 返回明确存在的 toolkit | 可列入 SDK 扩展契约；不返回伪造 provider |
| `GET /auth_configs` | 过滤、分页、ENABLED/DISABLED、稳定 ID | 已完成配置且通过准入的授权方式 |
| `POST /connected_accounts/link` | 接受 user_id、auth_config_id、callback_url，返回授权链接 | 网关先创建持久化连接事务 |
| `GET /connected_accounts` | 精确过滤用户、连接、auth config、状态与分页 | 只从归属映射查询，不能透传管理端全量列表 |
| `GET /connected_accounts/{id}` | 单条安全视图 | 建议补齐详情契约；无任何凭据 |
| `POST /connected_accounts/{id}/revoke` | 独立撤权、可重试、真实结果 | 使用拟新增 OpenConnector 非破坏性撤权接口 |
| `DELETE /connected_accounts/{id}` | 删除记录与凭据，幂等 | 与 revoke 区分；未知账户与跨项目对象不得泄露 |
| `POST /tool_router/session` | 固定用户、toolkits 和 connected_accounts | 创建受限 session 与执行凭据 |
| 响应中的 MCP URL | 可实际初始化、列工具及执行 | 指向兼容网关，不直接指向原生全局 MCP |
| `POST /tools/execute/{slug}` | 仅有真实调用方需要时扩展 | 显式维护 slug、输入、输出映射 |

Multica 当前连接 SDK 使用重复数组 query 参数；auth config 的 toolkit 过滤使用不同格式。序列化必须按实际 SDK 契约实现，不能凭名称统一处理。[M7][M8]

### 5.1 响应规则

目录和列表使用 SDK 预期的 `items`、`next_cursor` 等结构，不能原样转发 OpenConnector 的 `success/data/meta` envelope。[M7][M8][O3]

连接视图至少提供 SDK 消费的 `id`、`user_id`、`auth_config_id`、`auth_config.id`、`toolkit.slug`、`status`，其余字段按冻结的 fixture 填充。所有兼容 ID 都应稳定；不把上游原始 ID 冒充现有 Composio 连接。

错误采用 SDK 可解析的结构：[M9]

```json
{
  "error": {
    "message": "Connection is not available to this session.",
    "code": 403,
    "slug": "CONNECTION_NOT_ALLOWED",
    "status": 403,
    "request_id": "req_example"
  }
}
```

状态码、错误 slug 和脱敏策略都要进入测试。尤其不能将“功能不支持”返回为 404 来骗过 revoke/delete 的幂等处理，因为 Multica 会把部分 404 视作已完成。[M4][M7]

### 5.2 分页与过滤

分页必须在身份/权限过滤之后进行，游标绑定项目、过滤条件和稳定排序；建议游标包含版本与完整性校验，禁止跨项目复用。多种过滤条件采用交集，单个数组内的取值语义按客户端契约冻结。

`total_items` 不得包含用户无权获知的对象。未知字段不能默认造成权限放宽：未知限制字段拒绝；明确非安全元数据字段可按 profile 允许，并记录兼容告警。

### 5.3 Auth config 准入

首版每个项目每个 toolkit 选择一个明确配置，避免 Multica 动态选择时出现不确定性。`auth_config_id` 映射到运行时实例、provider、授权类型、配置版本与能力表。

只有 provider 已存在、授权配置完整、callback 与 scopes 可用、运行时可达、批准的 Actions 存在，才将其标记 ENABLED。自有 OAuth 配置不得被标成 `is_composio_managed=true`。[M8]

## 6. 身份与数据模型

建议建立以下逻辑实体，数据库表名可按项目规范调整。

| 实体 | 关键字段 |
|---|---|
| `projects` | project_id、控制凭据摘要、允许的回调来源、profile、状态 |
| `subjects` | project_id、external_user_id、状态 |
| `auth_configs` | compat_id、runtime_id、provider、auth_type、config_revision、capabilities |
| `connections` | compat_id、subject_id、auth_config_id、runtime_id、native_connection_id、alias、state、generation |
| `connect_transactions` | link_id、subject、auth config、callback、nonce摘要、上游request_id、阶段、期限、版本 |
| `agent_bindings` | project、agent、owner、grant_version、被批准的连接与Actions |
| `sessions` | session_id、subject、agent、任务关联、allowlist快照、token摘要、issued_at、expires_at、state |
| `executions` | logical_operation_id、session、connection、Action、参数指纹、状态、上下游execution_id |
| `outbox_jobs` | 事件/撤权/清理/状态同步任务、重试次数、租约、最后错误 |
| `audit_events` | 操作主体、资源、结果、策略版本、关联ID、脱敏元数据 |

核心约束：

- `(project_id, external_user_id)` 唯一；user_id 由可信 Multica 服务端指定，不由 Agent 指定。
- `(runtime_id, native_connection_id)` 的有效归属唯一，避免同一底层凭据被意外绑定给不同用户。
- 首版每 subject/toolkit 仅一个当前有效兼容连接；替换时保存历史 tombstone，不重用旧会话权限。
- 会话中的连接必须同时满足 subject、provider、auth config 与项目一致。
- 别名仅用于展示或底层选择；以稳定 native connection ID 为权限依据。
- 控制凭据与会话 token 只存摘要；调用 OpenConnector 所必需的运行时 Token 加密保存，管理员 Token 置于部署密钥存储。
- 兼容网关不保存第三方 OAuth access_token/refresh_token。

禁止直接复制、共用或 SQL 更新 OpenConnector 的内部业务表。两边事务不能假装是同一个数据库事务；用状态机、幂等键和补偿任务处理跨服务不一致。

## 7. 连接与 OAuth 状态机

### 7.1 标准流程

1. Multica 登录用户选择 toolkit；业务层解析 auth config 并创建签名 state。[M3][M4]
2. Multica 控制面调用兼容 `connected_accounts/link`；网关认证项目，保存 expected user、auth config、原始 callback 和期限。
3. 网关分配稳定兼容账户 ID，初始为 pending，返回链接页，不提前返回 ACTIVE。
4. 浏览器打开连接页，服务端确认交易未过期、未使用，再启动 OpenConnector 授权请求；保存原生 `connectionRequestId`。
5. OpenConnector 处理 provider OAuth；网关通过管理端轮询或受控同步确认实际结果，不信任 URL 中的 `status=success`。[O4]
6. 第三方授权成功后，底层凭据可以已存在，但兼容账户保持“待身份确认”，不能签发执行权限。
7. 浏览器返回 Multica 的兼容身份确认入口。该入口必须从真实登录 session 获取当前用户，通过服务端通道证明其与授权发起用户相同；不能由浏览器提交 user_id 即视为可信。
8. 网关完成主体核对和原生连接验证，原子激活兼容映射，返回回跳信息。
9. 回到原 Multica callback，保留原有 state，再追加 status 与 connected_account_id；现有所有权校验仍执行，不绕过。[M4]
10. 对被替代连接撤销旧会话，按 provider 能力处理旧授权；持久化状态同步任务。

第 7 步是拟新增的兼容模式加固；现有签名 state 证明“谁发起”，不能单独证明“打开链接并完成授权的浏览器是谁”。Composio 当前文档也提供回调身份校验机制，不能把单纯回跳等同于身份验证。[C3]

### 7.2 拟新增身份确认协议

可采用 `verify_ticket` 一次性票据：票据只引用交易，不包含第三方 Token；Multica 在登录后由服务端调用网关内部完成接口，传入从登录态获得的 subject。

票据必须短期有效、单次消费、限定项目与 callback；对用户不匹配的结果明确失败，并隔离未认领的原生连接。最终完成接口不直接暴露给 Agent。

现有桌面客户端无登录态时应引导到浏览器完成登录；缺少身份验证不能退回无校验激活。

### 7.3 多用户并发授权

已确认现有连接路由使用同一个 `local-admin` owner，请求存储按 owner/service 使旧 pending 请求失效。[O1][O2]

**开发期保底方案：** 在网关以 runtime/provider 为范围做跨副本互斥；冲突直接返回可重试的“该应用已有授权进行中”，不把等待时间藏在签名 state 生命周期内。锁和清理必须持久化，不能仅用进程 mutex。

**多用户生产推荐：** 给 OpenConnector 增加可选的可信 subject 上下文。建议在管理鉴权之后读取拟新增 `X-Connector-Subject`，映射到请求 owner；未启用扩展时保留 `local-admin`。subject 由网关根据项目与用户派生，浏览器、MCP 与普通运行时 Token 不能传入或覆盖。

创建、轮询、重连、同步与撤销授权事务都必须使用相同的 subject。此扩展只解决授权请求的命名空间，不自动构成完整多租户授权；连接归属仍由网关和精确 Token grants 强制执行。

### 7.4 期限、重复请求与晚到回调

Multica 当前默认 state 为五分钟，OpenConnector 授权窗口为十分钟，两者不能不经处理直接拼接。[M3][O4]

建议生产兼容配置将 Multica state TTL 设为十五分钟、兼容链接最长十分钟，并保留完成校验余量。这些是拟新增配置接线，真实值按端到端试验调整。任何层的硬期限过后，都不能仅凭晚到 success 恢复账户。

重复 callback 对同一交易返回一致的安全结果；已失败、已撤销、已替代交易不能被复活。回调处理与连接替换使用版本/CAS 判断。上游创建结果不明时，保存 reconciliation 状态，不自动重复创建 OAuth 链接。[O4]

对于底层已成功而本地映射提交失败的情况，后台对账应使用已保存的 request_id 恢复；无法可靠归属的连接进入隔离清理，不猜测最近创建的账号。

## 8. 任务级会话与密钥隔离

### 8.1 默认生产鉴权设计

当前 Multica 将项目 Key 随 MCP 配置下发，因此安全生产方案必须修改 session 鉴权接线，不能只改 BaseURL。[M5][M6]

建议兼容响应增加 **本项目扩展** `mcp.headers`：

```json
{
  "session_id": "trs_example",
  "mcp": {
    "type": "http",
    "url": "https://connector-mcp.example.com/sessions/trs_example/mcp",
    "headers": {
      "Authorization": "Bearer <session-only-token>"
    }
  },
  "config_version": 1,
  "warnings": []
}
```

这不是对 Composio 原有响应格式的事实声明，而是显式兼容扩展。Multica 的 official 模式保持旧行为；compat 模式必须取得合法会话 Bearer，否则失败，绝不 fallback 到项目 Key。

只允许预期 Authorization 头；MCP URL 必须匹配部署配置的 HTTPS origin 与路径规则。拒绝不可信域名、携带凭据的 URL 和跨域自动转发鉴权头。会话 token 不放在 URL；MCP 的授权规范也禁止把访问 token 放入 query。[P2]

本模式属于预配置 Bearer 会话，不宣称实现完整 MCP OAuth 授权服务器、客户端发现或动态注册。

### 8.2 Session 授权快照

每个会话保存项目、owner subject、agent_id、允许连接 ID、允许 Action ID、创建时策略版本、到期时间和当前状态。若有任务与调用者信息，保存在可信上下文及审计中；不能从 Agent 的 tools/call 参数获得这些权限事实。

兼容 CreateSession 可使用拟新增 `compat_context` 承载 agent_id、actor_user_id 和可用的任务上下文，仅在 compat 模式发送；official 模式不得污染外部协议。完整 task/run 关联在任务领取时补齐，并记录验证过的调用权限。

权限取交集：

```text
项目准入策略
∩ Agent 当前授权
∩ Agent 所有者当前有效连接
∩ 本次会话固定连接
∩ 本次 Action 白名单
∩ OpenConnector 当前部署/Token 策略
```

没有合法连接或 Action 时拒绝创建可执行会话。不把空数组传成 OpenConnector 的不受限连接 Token。[O3]

### 8.3 队列等待与长期任务

不能在任务入队时生成一个短 token，再假定任务立即开始。生产版本在 daemon claim/实际启动前验证会话；过期或策略变更则由可信 Multica 服务端重新计算、重新签发并更新 overlay。

具体任务领取代码落点由预检定位；这是必须覆盖的行为，不虚构现有 hook 已存在。

建议初始会话期限为六十分钟，且不超过本次任务批准的最大运行期限。该值是设计默认值，不是现有产品特性。对于超过期限的 CLI 任务，不假定运行时支持热换 header：明确使用重新启动/恢复流程，禁止把长期刷新 token 交给 Agent。

任务完成、取消、授权变更、Agent 删除或共享权限收回时，通过可靠 outbox 撤销相关会话。SDK 新建请求之前必须检查撤销状态；数据库或权限存储不可用时停止执行。

### 8.4 共享 Agent

保留 Multica 的所有者授权模型；调用者有权运行 Agent，不代表其可以管理所有者连接。[M5] 界面必须显式说明共享 Agent 会使用所有者选择的应用权限。

审计分别记录 account owner 与 initiating actor。第一版若不能在会话中安全传递 actor，则必须通过 Multica task/session 关联补足，不能把两者都记成 owner 后声称完整审计。

## 9. MCP 工具与目录控制

网关提供的基础工具建议保持 `list_apps`、`list_connections`、`search_actions`、`get_action_guide`、`execute_action` 的清晰分工；参数 schema 以固定 OpenConnector 基线获取的快照为依据。[O3]

不过，网关不能原样暴露底层管理目录。所有发现、schema、guide 和执行接口都用同一套策略过滤，避免执行受限但元数据泄漏。

- `list_connections` 只返回会话允许的安全标签和选择标识。
- `search_actions` 先做 provider/Action 授权，再搜索、分页与返回。
- `get_action_guide` 不包含管理员接口、内部地址、真实 Token 或未经授权账号信息；示例应指向当前网关调用方式。
- `execute_action` 只接受业务参数与受控连接选择；拒绝用户覆盖 runtime token、subject、上游 header、绝对 URL 或代理路径。
- Agent 指定其他 alias 或 native connection ID 时，必须重新验证所属关系，不允许默认回退到另一个账号。

首版每 toolkit 仅一个允许连接时，可以由网关固定该账号，避免 Agent 误选默认账号。未来支持多账号时，执行前强制明确选择，不能改变原会话目标。

使用官方 MCP SDK 完成协议协商与错误处理。测试包括 initialize、initialized、tools/list、tools/call、无效请求、取消、超时和超限。HTTP JSON 响应与长连接行为按实际协议版本验收，不能假定 GET SSE 必须存在；OpenConnector 原生端点本身为无状态 POST。[O3][P1]

## 10. Action 执行、幂等与写操作

### 10.1 选用 HTTP 作为底层执行通道

Agent 使用 MCP，网关将合法执行转换为：

```http
POST /v1/actions/:actionId
Authorization: Bearer <restricted-openconnector-runtime-token>
x-oo-connector-app-id: <exact-native-connection-id>
Idempotency-Key: <gateway-generated-operation-key>
Content-Type: application/json

{"input": {}}
```

这些底层 selector 与幂等能力已在 OpenConnector 文档中定义。[O3] 实施时仍要对生成 OpenAPI 和实际 handler 做契约测试。

不向执行路径提供管理员 Token；后台为会话创建或复用经过策略指纹绑定的受限运行时 Token。若复用，引用计数、撤销和策略变更必须可证明不会误伤或扩权；首版优先一会话一受限 Token，并做可靠回收。

### 10.2 幂等键

网关为“同一逻辑操作”分配不可预测操作 ID，结合项目、session、连接和 Action 生成足够唯一的 Idempotency-Key。OpenConnector 的键命名空间是 runtime-wide，不能只使用短任务号或重复的 JSON-RPC id。[O3]

同一业务输入不自动代表同一次操作：用户明确连续发送两次消息可能就是两个写入意图。传输重试复用原 operation ID；新意图分配新 ID。

网关内部重试可以稳定复用 ID；跨不同 MCP 请求的去重需要调用方或审批流程携带已持久化的 operation handle。不能承诺仅靠模型重新发起一遍调用就自动识别其为重试。第一版只读不依赖这一推断；开放写操作前必须补齐 operation/approval 关联。

执行记录建议使用：`PREPARED → DISPATCHED → SUCCEEDED/FAILED/UNKNOWN`。UNKNOWN 不自动变为 FAILED，也不自动重发；先用 provider 可用的业务查询对账，无法确认则交给人工处理。

OpenConnector 当前同键结果的重放窗口为二十四小时，且不保证第三方 exactly-once。[O3] 网关重试窗口不能超过底层有效窗口后仍声称可安全重放。

### 10.3 写操作上线条件

写操作必须使用明确 Action allowlist 和必要的参数级限制；例如限定测试仓库、频道、收件域或资源集合。metadata 中的 readOnlyHint 等提示不能作为安全授权依据。

涉及发信、删除、对外发布或资金等高影响操作，在缺少可信用户审批通道前保持关闭。审批应绑定操作类型、账号、参数指纹、审批用户和期限；不能由 Agent 自报“用户同意”代替。

通用 proxy、远程 Bash、代码工作台默认关闭，以免绕过 Action 白名单。将来开放时必须建立独立能力和审计，不复用“能执行某个工具”作为任意网络调用授权。

## 11. 撤销、删除与连接替换

### 11.1 不能使用的简单映射

不能把 Composio `revoke` 直接转换为 OpenConnector 现有 `DELETE ... {revoke:true}` 然后只判断 HTTP 200。现有底层接口可能已删除凭据而撤权失败，造成后续无法利用原凭据重试；它与 Multica SDK 分开的 revoke/delete 语义不相同。[O3][M4][M7]

### 11.2 推荐的拟新增 OpenConnector 能力

增加受管理员鉴权和实例隔离保护的独立撤权入口，例如：

```http
POST /api/connections/by-id/:appId/revoke
```

这是拟新增接口，准确命名在实施时按上游路由规范确认。要求：稳定 ID 定位、可重试、独立返回撤权结果、失败时保留必要的加密凭据与恢复信息、不因未完成撤权删除记录。

实施时复用 OpenConnector 现有 OAuth refresh/revoke 服务，不把 provider 凭据导出到网关。provider 无对应远程撤权能力时返回 unsupported；不要制造成功结果。

### 11.3 网关流程

1. 在网关将连接置为 REVOKING，增加 generation，撤销引用它的会话，立即阻止新的执行 admission。
2. 调用独立上游撤权；记录 done、unsupported、retryable failure 或 outcome unknown。
3. 成功时置 REVOKED，供后续 DELETE 幂等清理。
4. 失败时保持不可执行，后台重试或人工介入，不恢复 ACTIVE。
5. 不支持时明确显示“本地已禁用，上游授权未确认撤销”；严格兼容模式返回明确非 2xx 能力错误，而不是 404 或伪造成功。
6. 清理本地凭据与兼容映射是独立步骤，保留最小 tombstone，避免重复回调复活。

生产目录可选择只开放已支持远程撤权的 OAuth provider，其他连接保留为显式“本地断开”产品能力。Multica 界面和状态同步必须区分这两者。

新执行应即时被阻止；撤销前已被第三方接收的操作无法保证取消，也不能保证回滚。对此在审计中标明在途执行，不声称全局零竞态。

某些 provider 的撤权可能影响同一授权项目下其他连接。OpenConnector 文档特别提示 Google 的授权撤销影响可能跨同项目多个 OAuth 客户端。[O3] 上线前必须建立 provider 级影响说明，并在需要时要求用户确认。

### 11.4 替换与重新授权

新连接成功并完成身份确认前，旧连接不被无条件覆盖。切换时同时增加连接/Agent grant generation，撤销旧 session。仅刷新凭据或更换实际第三方账号的语义不同，不能让旧 session 自动获得另一个账号。

不要机械地在新授权完成后撤销旧 Token：若新旧连接共享同一 provider grant，撤旧授权可能同时使新连接失效。替换策略必须按 provider 选择本地停用旧引用、先完整撤权后重新授权，或明确确认的其他流程；不能在没有影响分析时自动撤权。

## 12. Multica 改动清单

以下按修改边界组织，具体文件位置由执行代理在基线与用户 fork 中核对。

| 改动 | 内容 | 级别 |
|---|---|---|
| 配置接线 | 新增 backend 模式与 BaseURL；official 为默认 | 必需 |
| 会话响应 | 可选读取本项目 mcp.headers 扩展 | 必需 |
| overlay 构建 | compat 使用会话 Bearer；禁止 project Key fallback | 必需 |
| 领取/启动前校验 | 处理排队导致的会话过期和权限变化 | 生产必需 |
| 授权身份确认 | 兼容模式完成 OAuth 前确认浏览器登录用户 | 生产必需 |
| 会话上下文与撤销 | Agent、actor、task 关联；权限变化和任务结束触发撤销 | 生产必需 |
| UI/生命周期状态 | 显示 OpenConnector 后端；断开/待撤权/异常重连区别 | 生产必需 |
| 契约与回归测试 | official 路径不变、compat 路径无密钥泄漏 | 必需 |

建议新增配置，名称可按仓库规范调整：

```dotenv
# 以下是拟新增配置，不是宣称当前上游已支持
COMPOSIO_BACKEND=official
COMPOSIO_BASE_URL=
COMPOSIO_CONNECT_STATE_TTL=15m
COMPOSIO_COMPAT_MCP_ORIGIN=https://connector-mcp.example.com
```

启用 compat 时显式设置模式和地址。SDK 已有 BaseURL 能力，但启动接线仍需实现。[M1][M2]

`mcp.headers`、兼容上下文和身份验证扩展都只能在 explicit compat 模式使用。official 模式仍按原 SDK 协议工作，不向 Composio 发送未知扩展字段，不改变原默认设置。

优先修改的已知路径：[M1–M6]

```text
server/pkg/composio/client.go

server/internal/integrations/composio/service.go
server/internal/integrations/composio/dispatch.go
server/cmd/server/router.go
```

任务领取、权限更新和 UI 的具体文件由预检定位。不要为了方案看起来精确而虚构不存在的 hook 或配置项。

## 13. OpenConnector 改动清单与不改核心的边界

网关不复制 provider executor，不重写 OAuth 流程，不直接修改底层数据库。

生产建议提交两个小范围、默认不改变现有行为的通用改动：

**OC-1：可信 subject-scoped 授权事务。** 管理接口启用扩展时按可信 subject 建立 owner；创建、轮询、重连与同步一致。旧无扩展请求仍为 local-admin。补跨用户、跨项目、伪造 header 和旧行为回归。

**OC-2：独立撤权。** 提供不先删除凭据的撤权操作、结果状态与重试路径，保留原有 DELETE 行为以避免破坏已有用户。补不支持、网络失败、重复撤权、替换竞态、订阅资源清理与凭据保密测试。

如上游暂不接受，只在用户获准的 fork 上维护最小 patch queue，并固定补丁提交。不能隐瞒补丁依赖而宣称“完全不改 OpenConnector”。

不改 OC-1 时可使用每 provider 互斥授权的保底模式，但须披露并发限制；不改 OC-2 时不能宣称严格分离的 revoke/delete 已完成。可以做只读技术原型，不能绕过能力门槛上线完整生命周期。

## 14. 错误、重试与限流

| 情况 | 建议兼容行为 |
|---|---|
| 参数或 schema 不合法 | 400 / INVALID_INPUT |
| 缺失、伪造或过期执行 token | 401，不能使用控制 Key 兜底 |
| 连接或 Action 越权 | 403；按隐私模型必要时对对象存在性统一隐藏 |
| 不存在对象 | 404；不得拿该码表示“功能未实现” |
| 处理中、幂等冲突、并发授权限制 | 409，明确可恢复方式 |
| 限流 | 429，保留安全的 Retry-After |
| 声明支持但临时不可用 | 502/503，错误体不含上游秘密 |
| 未实现的 API/能力 | 501 / UNSUPPORTED_CAPABILITY |
| 超时后副作用不明 | 安全错误 + UNKNOWN execution 状态；不自动重放 |

HTTP 错误和 MCP 工具业务错误分别遵循各自契约。不能把 HTTP 200 一概当作 provider 操作成功，也不能把工具业务失败伪装成协议成功结果。

读取请求可有限退避重试；OAuth link 创建、session mint 和写 Action 必须先建立幂等/对账边界。统一按项目、subject、session 与 provider 设置速率及并发上限，不能只做全局限流。

日志包含 request_id、session_id、execution_id、action_id、脱敏连接标识、policy_version 与阶段耗时。不默认记录完整请求/返回体；调试采样也必须经过敏感字段过滤。

## 15. 安全威胁与强制防护

| 威胁 | 防护与验收 |
|---|---|
| Agent 获得项目管理权限 | 双凭据、双入口、网络隔离；提取会话 token 后仍无法调用管理 API |
| A 用户访问 B 用户账号 | 稳定 ID 归属、SQL 项目范围、会话 pinning、精确原生 grants |
| 空白名单扩权 | 空集合不签发；不得生成 allowedConnections=[] 的执行 token |
| OAuth 链接被转发 | 完成前 Multica 登录身份确认；一次性票据 |
| 同 provider 授权互相覆盖 | 可信 subject owner；保底模式则跨副本互斥 |
| 晚回调复活旧连接 | CAS/generation、终态保护、隔离未认领连接 |
| 任意 action/alias 绕权 | schema、ID 与业务资源边界统一校验 |
| SSRF/凭据转发 | 固定 upstream、callback origin 白名单、禁止任意代理与跨域 header 转发 |
| 写入重复 | 稳定 operation ID、HTTP 幂等、UNKNOWN 对账，禁止盲重试 |
| 撤销后仍能使用旧会话 | admission 前强校验状态、版本与撤销记录；失败关闭 |
| 元数据泄漏 | discovery/schema/guide 与 execute 同策略 |
| 数据恢复复活 token | 恢复后轮换/废止历史会话，暂停清理/触发器，重新核对连接状态 |

TLS、密钥轮换、受限数据库角色、依赖锁定、镜像扫描和安全审查均为交付项。访问第三方返回内容是工具结果，不是可改变系统权限的指令。

## 16. 测试与沙盒联调

### 16.1 三层验证

**L1：离线契约与故障注入。** 使用 mock OAuth provider、mock OpenConnector 和真实 Multica SDK；所有 CI 单测无需真实个人账号。测试 malformed response、超时、429、分页、重复 callback、失效锁、服务重启和多副本竞争。

**L2：真实 OpenConnector 本地环境。** 固定提交构建，使用 PostgreSQL、独立密钥与受控网络。验证真实 HTTP 路由、Token grants、subject 扩展、撤权扩展、幂等及审计行为。

**L3：第三方测试账号。** 使用专门注册的开发 OAuth 应用及自有测试数据，只读优先。第三方没有官方沙盒时明确标为真实服务测试账号，而非声称有 sandbox。先验证 provider 身份，再验证读取、取消、撤权和重新授权。

任何写测试限制在批准的测试仓库/邮箱/频道；测试负责人显式批准后执行。没有真实凭据时可交付 L1/L2，不得将 L3 标为通过。

### 16.2 核心验收用例

### 16.3 质量门槛

建议安全与状态机包达到不少于 90% 的分支覆盖目标，普通模块不少于 80%；覆盖率只是辅助指标，上述安全场景必须全部通过。最终百分比由项目测试工具可测口径确定，不能把该目标写成已有实测结果。

网关压测可以先设定“受控 stub 环境下新增 p95 延迟不超过 100ms”的目标，并附并发、请求率、机器和数据库配置。真实 provider 延迟单独报告，不与网关开销混为一谈。

禁止以自己写的假 SDK 代替真实 Multica 客户端；内部 service 测试应放在 Multica 合法包路径中，不能绕过 Go internal 包限制。

## 19. 部署、配置与运维

### 19.1 部署顺序

先创建独立测试域名与密钥；迁移网关和 OpenConnector 各自数据库；启动运行时并核验 capability；注册 OAuth callback；启动网关控制面与 MCP；最后启用测试 Multica 的 compat 模式。

生产镜像固定 tag 加 digest 或由明确提交构建的 digest，不使用浮动 latest。源码 main 不自动等于已发布镜像；必须记录实际构建的 commit 与制品摘要。

OpenConnector PostgreSQL 迁移需要按其发布规范显式执行；不能把启动成功当作已完成所有迁移。[O5]

### 19.2 示例配置类别

建议网关提供以下拟新增配置，具体名称以实现为准：

```dotenv
COMPAT_PROFILE=multica-core-v1
CONTROL_LISTEN=:8080
MCP_LISTEN=:8081
PUBLIC_CONNECT_ORIGIN=https://connector-connect.example.com
PUBLIC_MCP_ORIGIN=https://connector-mcp.example.com
OPENCONNECTOR_BASE_URL=http://openconnector:3000
OPENCONNECTOR_ADMIN_TOKEN_FILE=/run/secrets/oc_admin_token
DATABASE_URL_FILE=/run/secrets/gateway_database_url
SESSION_TTL=60m
CONNECT_LINK_TTL=10m
EXECUTION_MODE=read_only
PROXY_ENABLED=false
TRIGGERS_ENABLED=false
```

此片段是配置设计，不是可直接执行的部署包。最终必须补齐镜像、TLS、网络策略、健康检查、迁移 job 和真实 Secret 引用，不能在文档中填入真实值。

### 19.3 监控与告警

关注授权完成率、回调拒绝原因、session 签发和撤销、跨用户拒绝、原生 401/403/429、UNKNOWN 执行、撤权失败、孤儿连接、审计未持久化、依赖版本漂移与旧 Token 清理积压。

建议任何越权成功或项目 Key 泄漏立即停止兼容数据面；UNKNOWN 写入与撤权失败形成可追踪任务，不只打印日志。

状态同步不能只依赖浏览器回跳。网关应对持有的连接做限速对账，并通过可靠事件或 Multica reconcile 接线更新状态；短暂网络失败不直接标作 EXPIRED。

### 19.4 恢复与密钥轮换

备份数据与加密密钥必须分开管理。恢复到旧快照后，历史有效 Token 可能被重新带回，因此恢复流程要先废止/轮换执行会话，再与 OpenConnector 核对连接状态，之后才能开放入口。

跨系统没有“原子恢复”。记录一组关联快照和版本，隔离可能已在第三方撤销但在备份中仍 ACTIVE 的连接。禁止恢复后直接重试历史 UNKNOWN 写操作。

## 20. 迁移与回滚

### 20.1 第一版建议隔离部署

使用新的测试 Multica 部署/数据库或明确的隔离环境重新授权，避免现有 `user_composio_connection` 记录被误认为兼容后端记录。

切换 BaseURL 不会把真实 Composio 的连接 ID、授权配置或第三方凭据迁移到 OpenConnector。原有 `ca_*` ID 不能凭名称映射到一个新账号；用户需要重新授权，除非有独立、验证过且获准的数据迁移流程。[M4][M7]

### 20.2 真实共存

首版不承诺同一 Multica 集成槽同时连接两个后端。如需共存，增加显式 backend namespace/connection ownership，数据库记录必须区分来源；网关不得在某个后端失败后自动换用另一账号。

原生独立 MCP 与兼容 Composio 槽可以作为不同实验路线，但不能同时挂载到同名 server 并依赖不确定的覆盖顺序。[M5]

### 20.3 回滚流程

停止新任务与新授权，撤销兼容 session，排空或隔离在途执行，保存审计/UNKNOWN 清单，再切回独立保留的 official 部署与配置。第三方已完成副作用不会因应用回滚而撤销。

采用 expand/contract 数据库迁移，避免同一发布删除旧字段。网关和 OpenConnector 补丁分别可回滚，但回滚后不再支持的安全特性必须使 compat 功能停用，不能自动退回不安全模式。

## 21. 上游升级策略

维护 `compatibility-manifest.yaml`，记录固定提交、镜像、Multica/MCP 运行时版本、接口集合、工具 schema 摘要、OpenConnector 补丁、provider 能力与实测日期。模板见同目录文件。

升级流水线按以下顺序执行：

1. 在专用升级分支更新一个依赖，不同时升级三层。
2. 比较 Multica SDK/业务调用、回调、overlay 与任务领取变化；比较 OpenConnector 路由、owner、Token policy、Action schema、撤权与迁移变化。
3. 自动生成差异报告；未知限制字段、新 auth scopes、新 Action、权限默认值变化必须人工审查。
4. 运行旧基线回归与新候选契约；新 schema 通过不代表旧客户端还能工作，必须双向验证。
5. staging 只读验证，再测试生命周期，最后 canary；失败回到上一组已验证 manifest。

新 provider、新 Action 或 schema 变化不自动加入现有会话白名单。受限 Token 和 session 使用固定 ID 集合；如业务刻意采用通配符，必须明确接受未来新增 Actions 的风险，首版不启用。

可以将版本检查和契约 CI 配置成仓库定时工作流；本方案未替用户创建任何自动化任务。

## 22. 最终交付与上线检查

完整交付至少包括：网关代码与迁移、Multica 补丁、OpenConnector 补丁或明确保底限制、契约快照、自动化测试、真实联调记录、镜像摘要、配置模板、Secret/网络策略、部署/恢复/回滚手册、兼容矩阵和已知限制。

上线前必须同时满足：

- 固定基线的真实 Multica SDK 与目标 Agent 运行时通过。
- 无项目 Key/管理员 Token/第三方凭据进入 Agent。
- 两用户同 provider 授权、越权拒绝、重复/晚回调测试通过。
- 空白名单不扩权，撤销与策略变更使新执行被拒绝。
- 真实 provider 的撤权行为有证据；本地断开不冒充远程撤权。
- 长队列和 token 到期恢复路径验证过。
- 不存在未说明的写操作重试或 UNKNOWN 重放。
- 备份恢复、版本升级、canary 与回滚演练通过。
- 所有尚未实现的接口、元工具和 provider 能力在 manifest 中标注 unsupported。
